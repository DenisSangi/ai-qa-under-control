# player-service mutants

One faulty version per numbered requirement of `docs/spec/SPEC.md`. M01–M54 are in specification
order. M55–M64 were added afterwards, also in specification order. They cover requirements the
code fails only in some of the operations or steps they cover; each breaks a part the code meets,
and the "Part broken" column names the part that already fails. Each patch applies to the original
code on its own:

```bash
git apply mutants/M01.patch          # apply one mutant
mvn -B -q -DskipTests package        # build it
git checkout -- player-service/src/main   # back to the original
```

**Summary:** 69 numbered requirements · 64 patches (table 1) · 5 without a patch (table 2: 4 already
not met in every operation they cover, 1 cannot be broken within the rules).

**Conventions used in the tables**

- Java paths are relative to `player-service/src/main/java/com/arcade/player/`; `resources/…` is
  relative to `player-service/src/main/`.
- Players are created through the API. Money operations carry a fresh `Idempotency-Key`
  unless a key is named. A balance is set up with deposits ≤ 10000, which the stub approves.
- "clock +25H" = `POST /api/test/clock/advance {"duration": "PT25H"}` (likewise `S`); "clock +31D" =
  `{"duration": "P31D"}`. "stub" = payment provider stub
  and its admin API (section 10). "journal" = table `transactions`.
- "spec …" is the result the specification requires; "→ …" after it is the result with the patch.
- **After the clock moves** / **Concurrent only** mark mutants that show only under that condition.

## 2. Requirements without a patch

| Requirement | Reason |
|---|---|
| GEN-06 | **Already not met** in every endpoint it covers. `web/GlobalExceptionHandler.java:84`: there is no handler for `MethodArgumentTypeMismatchException`, so the catch-all `@ExceptionHandler(Exception.class)` answers a non-numeric `{id}` with `500 INTERNAL_ERROR` on every `/api/players/{id}…` endpoint (get, deposit, withdraw, stats, deposit-limits) and every `/api/sessions/{id}…` endpoint (get, finish); the code `BAD_REQUEST` is never produced, so no part is met. |
| GEN-18 | **Already not met** for both operations it covers (deposit and withdrawal). `service/PaymentClient.java:24` builds the RestClient without any timeout (Spring Boot 3.3's default request factory has none), and `:61-63` map every transport error to `502 PAYMENT_UNAVAILABLE`; `504 PAYMENT_TIMEOUT` is never produced. With stub `fixedDelay` 7000 a deposit waits 7 s and returns `200`. |
| GEN-19 | **Already not met** for both operations it covers. With no timeout (`service/PaymentClient.java:24`), a provider that answers after more than 5 s is waited for and its approval is applied: balance, journal and event change and the key is consumed. The `504` state the rule protects never arises, so no change can make the rule fail. |
| WDR-03 | **Already not met** in the only operation it covers. `service/PlayerService.java:92-99`: `withdraw` checks the range and the balance only, never the player's sessions; with an ACTIVE session a withdrawal returns `200` instead of `409 ACTIVE_SESSION_EXISTS`. Its sentence "an EXPIRED session does not block a withdrawal" holds only because there is no session check at all; breaking it would mean adding that check, not breaking a met part. |
| LDB-05 | **Cannot be broken within the rules.** Three independent paths keep the top fresh after a finish: the refresh after each finish (`service/GameService.java:111`), the 5-second schedule (`service/LeaderboardService.java:78`, `resources/application.yml:50`) and the 30-second cache TTL with recompute on a miss (`service/LeaderboardService.java:65-75`, `resources/application.yml:47`). Either of the first two keeps GET and the WebSocket within 30 s; the TTL alone still keeps GET within 30 s. Disabling all three takes several coordinated changes. Because the schedule and the TTL also cover period boundaries, that would also break LDB-07 and contain M54, so it is not one small, narrow mistake. |
